# 설계 결정과 배운 점

논문 실험 208건을 돌리며 하나씩 겪고 고친 것들입니다. 코드의 이상한 부분에는 대개 이 중 하나가 이유로 붙어 있습니다.

## 1. 큐 파일은 사람과 러너가 같이 고치는 문서다

큐를 DB나 러너 메모리에 두지 않고 YAML 파일에 둔 이유는, 실험 계획이 하루에도 몇 번씩 바뀌기 때문입니다.
결과를 보고 "이 가설은 버리자, 대신 이 대조군을 넣자"가 일상이고, 그걸 에디터로 하는 게 가장 빠릅니다.
그래서 러너는 다음 항목을 고를 때마다 파일을 다시 읽고, 항목 하나의 상태를 바꿀 때도 **파일을 다시 읽어 그 항목만 고쳐**
저장합니다(`queue.update_item`). 러너가 메모리에 들고 있던 목록으로 저장하면 그사이 사람이 추가한 항목이 사라집니다.
`tests/test_queue.py::test_update_item_rereads_file_so_concurrent_edits_survive`가 이 약속을 지킵니다.

## 2. 파싱 실패는 멈춤이다

YAML을 편집하다 저장하는 순간 러너가 읽으면 파일이 반쯤 쓰여 있을 수 있습니다. 처음 버전은 이때 "읽을 수 없으니 빈 큐"로
처리했는데, 그다음 상태 저장이 빈 목록을 그대로 써서 큐가 통째로 날아갔습니다. 지금은 몇 번 더 시도한 뒤 예외를 내고 멈춥니다.
멈춘 러너는 keepalive가 5분 뒤 다시 띄우고, 그때는 파일이 멀쩡합니다.

## 3. 모르면 거절한다

lock 파일의 PID가 살아 있는지 확인할 수 없을 때(권한, tasklist 실패) 러너는 "살아 있다"로 보고 물러납니다.
러너가 하나 덜 뜨는 비용은 5분 뒤 keepalive가 메우지만, 둘이 뜨는 비용은 두 실험의 시간과 결과 신뢰성입니다.
비대칭이 명확하면 보수적인 쪽을 고릅니다.

## 4. `running` 복구는 lock을 잡은 뒤에만

`running`인데 러너가 없는 항목은 죽은 러너의 흔적입니다. 하지만 "러너가 없다"는 판단은 lock을 잡아야 확실해집니다.
lock 없이 복구하면 살아 있는 러너의 현재 항목을 `pending`으로 돌려 두 번 돌릴 수 있습니다.

## 5. 밤에는 긴 것부터

낮에는 짧은 실험을 돌려 결과를 보고 다음 계획을 세우고, 밤에는 사람이 없으니 긴 실험을 돌립니다.
정렬 키가 `(priority, ±est_min)`인 이유입니다. `priority`가 먼저라서, 급한 긴 실험은 낮에도 바로 돕니다.

## 6. 이어서 돌리기는 하위 작업의 책임이고, 재개 키에는 설정 해시가 들어가야 한다

lanerun은 결과 파일을 모릅니다. 논문 저장소에서는 학습 스크립트가 "결과 파일이 있는 시드는 건너뛴다"로 재개를 처리했습니다.
그런데 코드 감사에서, **설정을 바꿔도 같은 이름의 옛 결과를 재사용하는** 버그가 나왔습니다. 결과 파일 이름에 설정의 해시를 넣어
고쳤고, 그 뒤로 결과 JSON마다 git 해시·설정 해시·라이브러리 버전·시드를 기록합니다. 재현성은 나중에 붙이는 게 아니라
저장 형식을 정할 때 생깁니다. lanerun이 이 로직을 품지 않는 이유는, 무엇이 "같은 실험"인지는 실험 코드만 알기 때문입니다.

## 7. STATE.md는 스냅숏이다

처음에는 로그를 덧붙이는 파일이었는데, 길어질수록 세션 시작 때 읽는 비용이 커졌습니다. 지금은 매번 통째로 다시 씁니다.
레인별 개수, 다음 항목, 최근 완료 10건, 실패 목록, 마지막 오류. 코딩 에이전트에게 "STATE.md를 먼저 읽어라"라고 적어 두면
그다음 질문이 줄어듭니다. 이력은 git이 가지고 있습니다(원본 저장소에서 STATE.md 커밋 64개).

## 8. 가드는 끼우는 자리다

GPU 온도 가드는 `guards.TemperatureGuard` 하나뿐이지만, `read` 함수와 `sleep`을 주입받게 해 두었습니다.
디스크 여유 공간, 특정 시간대 금지 같은 조건이 필요하면 같은 모양으로 추가하면 됩니다. 테스트는 온도를 주입해 기다림 횟수만 봅니다.

## 9. 일부러 안 만든 것

- 자동 재시도: 실패한 실험을 그냥 다시 돌리면 같은 이유로 또 실패하면서 GPU 시간만 씁니다. 사람이 로그를 보고 `reset`합니다.
- 의존성 그래프: 200건 규모에서는 `priority`와 큐 순서로 충분했습니다. 필요해지면 `after: [id]` 필드를 넣을 자리는 있습니다.
- 분산 실행: PC 한 대가 전제입니다. 두 대가 되면 lock과 큐 파일을 공유 저장소에 두는 것보다 다른 도구를 쓰는 게 맞습니다.

## 10. 원본과 달라진 점

원본(`src/queue_runner.py`, 209줄)은 논문 저장소의 `src.run`을 직접 호출하고 레인이 `gpu`·`cpu`로 고정이었습니다.
lanerun은 `cmd`만 받고, 레인 이름을 받고, Windows(`tasklist`)와 POSIX(`os.kill`)를 모두 지원하고,
`init`·`add`·`validate`·`reset` 명령과 테스트·CI를 붙였습니다. 동작 규칙은 그대로입니다.
